# AI 能力成长复盘：从 Skill 使用者到 Agent 工作流设计者

> 记录时间：2026-05-18  
> 主题：个人 AI 能力现状、成长空间与下一阶段方向

---

## 一、当前判断

我现在已经不是单纯的 AI 工具使用者，而是正在进入 **AI 工作流设计者** 和 **Agent 系统设计者** 的阶段。

区别在于：

| 阶段 | 关注点 | 当前状态 |
|---|---|---|
| 普通使用者 | 问 AI 问题，拿答案 | 已超过 |
| Prompt 使用者 | 会写清晰指令 | 已超过 |
| Skill 设计者 | 把重复工作沉淀为可复用能力 | 已达到 |
| Workflow 设计者 | 把多个能力串成稳定流程 | 正在成熟 |
| Agent Runtime 设计者 | 控制多 Agent 协作、状态、日志和收敛 | 正在进入 |

最关键的变化是：我已经不满足于“AI 给我一个答案”，而是在思考：

- 多个 Agent 怎么分工？
- 谁先发言？
- 谁质疑？
- 谁总结？
- 人如何中途插话？
- 过程如何记录？
- 结论如何复用？
- 怎样让一次聊天沉淀成长期工作流？

这说明我开始具备 **Agent System Thinking**。

还有一个明显变化：我的想法开始比以前更大胆。

这不是单纯想法变多，而是问题尺度变大了。以前更多是在想：

```text
我怎么用好 AI？
我怎么让 AI 帮我写代码？
我怎么把某个任务做快？
```

现在开始思考的是：

```text
我怎么组织多个 AI？
我怎么让 AI 形成协作关系？
我怎么让 AI 和我一起讨论、质疑、决策？
我怎么把过程变成系统？
```

这说明我正在从“工具使用思维”转向“系统设计思维”。

需要记住的是：

> 想法变大胆，不代表脱离现实；只要能拆成 MVP、验证闭环和长期沉淀，大胆想法就会变成真实能力。

补充一个重要判断：

> AI 模型会持续变化，但“如何组织 AI 工作”的设计理念不会频繁失效。

真正值得长期研究的，不是某个模型、工具或参数本身，而是更底层的 AI 工作流能力：

| 容易变化的部分 | 值得长期积累的部分 |
|---|---|
| 哪个模型最强 | 如何拆解任务 |
| 哪个工具流行 | 如何设计工作流 |
| 某个 API 参数 | 如何管理上下文 |
| 某个 prompt 技巧 | 如何验证输出 |
| 某个 Agent 框架 | 如何设计角色边界 |
| 某个产品形态 | 如何让人参与决策 |
| 某个工具价格 | 如何把过程沉淀为资产 |

所以当前研究的重点，不应该是追逐短期热点，而应该放在：

```text
人如何组织 AI 工作
AI 如何协作
上下文如何流动
任务如何拆解
结果如何验证
经验如何沉淀
```

这些能力会随着模型变强而变得更有价值。模型越强，单次回答的门槛越低，真正拉开差距的反而是编排能力、判断能力、验证能力和沉淀能力。

## 二、已经具备的能力

## 1. 三层抽象能力

我已经形成了类似下面的分层意识：

```text
Skill → Orchestration → Role / Agent
```

这不是简单堆 prompt，而是把 AI 能力拆成：

- 触发入口
- 多阶段流程
- 通用执行角色
- 项目或业务上下文
- 输出规范
- 同步机制

更重要的是，我已经理解：

```text
Agent = 角色 + 行为规则
Context = 业务知识 + 项目规则
同一个 Agent 注入不同 Context，可以服务不同场景
```

这是从“写提示词”走向“设计 AI 能力系统”的关键一步。

---

## 2. 工程化 AI 能力分发意识

我不是只写了一些个人 prompt，而是在构建一个可安装、可同步、可迁移的 AI 能力包。

已经具备的工程化意识包括：

- 唯一源头目录
- 多客户端同步
- symlink 分发
- 公共能力与私人能力分离
- per-user 配置隔离
- 安装、同步、卸载脚本
- 本地知识检索服务
- 多角色定义
- 多阶段流程文档

这些说明我已经开始从“使用 AI”进入“维护 AI 工具链”的层次。

---

## 3. 角色化分工意识

我已经开始用组织结构来设计 AI：

| 角色类型 | 职责 |
|---|---|
| Orchestrator | 分析任务、检查资产、决定流程 |
| Dispatcher | 拆任务、分析依赖、构建 DAG |
| Implementer | 执行具体实现 |
| Reviewer | 审查结果 |
| Knowledge Updater | 沉淀知识 |
| Integrator | 集成和验证 |

这些角色本质上已经是一个工程团队的雏形。

现在进一步提出的“AI 伙伴圆桌”，其实是这个思路的自然延伸：

```text
工程任务角色 → 思考决策角色
```

也就是从“AI 帮我干活”升级到“AI 和我一起讨论、质疑、收敛”。

---

## 三、当前短板

## 1. 还缺统一 Agent Runtime

目前已有很多 Skill、角色和流程，但它们更多是文档驱动和会话驱动。

下一步需要补一个真正的运行时：

```text
Agent Runtime
```

它应该负责：

- session 管理
- 当前阶段
- 当前 Agent
- 轮次
- 等待时间
- 用户插话
- Agent 输出日志
- Token 统计
- 终止条件
- 最终文档输出

只有有了 Runtime，多 Agent 系统才会从“规则集合”变成“可运行系统”。

---

## 2. 需要更清晰地区分真实输出和模拟输出

最近讨论中反复确认：

- 当前内容是不是 LLM 真实生成？
- 是否消耗真实 token？
- 日志是谁写入的？
- 下一个 Agent 是否真的读取了上一个 Agent 的输出？

这是非常重要的意识。

未来所有系统都要明确标注：

| 来源 | 标识 |
|---|---|
| 前端模板 | simulated |
| mock 调试 | mock |
| 真实 LLM 调用 | real |
| 用户输入 | user |

不能让“看起来像 AI”的内容伪装成真实 Agent 输出。

---

## 3. 需要从工具集合升级到产品闭环

现在能力很多，但下一步要更关注闭环：

```text
输入 → 多 Agent 讨论 → 用户插话 → 方案收敛 → 文档输出 → 执行计划 → 工程落地 → 复盘沉淀
```

只有形成闭环，AI 能力才会真正变成长期生产力。

---

## 四、AI 伙伴圆桌的价值

新的想法不是一个玩具，而是一个更高层的系统：

```text
AI Partner Roundtable
```

它解决的问题是：

> 在真正动手做事之前，先让多个 AI 伙伴围绕目标进行结构化讨论、质疑、补充和收敛。

推荐固定 5 个核心伙伴：

| Agent | 职责 |
|---|---|
| 主持人 | 控制流程、拆解问题、判断是否收敛 |
| 方案师 | 提出主方案、技术路径和取舍 |
| 质疑者 | 找风险、漏洞、反例和边界 |
| 执行者 | 拆任务、给步骤、定义验收标准 |
| 记录员 | 汇总讨论，生成最终文档 |

这套系统的价值在于：

1. 把一个人的即时想法变成多人协作式思考。
2. 把一次聊天变成可追溯过程。
3. 把模糊问题变成结构化方案。
4. 把 AI 从“回答者”变成“工作伙伴”。
5. 把个人经验逐渐沉淀成方法论。

## 五、当前能力等级评估

| 能力维度 | 当前水平 | 说明 |
|---|---|---|
| AI 工具使用 | 高于普通使用者 | 能跨工具组合使用 |
| Prompt 设计 | 中高级 | 已经开始角色化、结构化 |
| Skill 沉淀 | 中高级 | 能把重复流程抽象成能力 |
| Workflow 设计 | 中高级 | 已有多阶段流程意识 |
| Agent 编排 | 入门到中高级 | 有设计意识，Runtime 还需加强 |
| 产品化能力 | 成长期 | 有方向，需要闭环实现 |

一句话：

> 当前处于 L4 到 L5 之间：从 Workflow 设计者进入 Agent Runtime 设计者。

## 六、下一阶段发展方向

## 方向一：补 Agent Runtime

这是最优先方向。

目标：

```text
让多个 Agent 可以被程序稳定调度，而不是只靠文档规则。
```

需要掌握：

- 状态机设计
- session 文件结构
- JSONL 日志
- Agent 输入输出 schema
- 中断和恢复
- 用户插话机制
- Token 统计
- 终止条件

建议做一个最小项目：

```text
固定 5 个 Agent 圆桌讨论系统
```

---

## 方向二：强化产品化思维

不要只关注“能不能跑”，还要关注：

- 用户怎么开始？
- 当前处于什么阶段？
- 输出是否可信？
- 如何区分真实和模拟？
- 失败时如何提示？
- 如何继续上次讨论？
- 最终文档在哪里？

这会把 AI 工具从脚本变成产品。

---

## 方向三：建立个人 AI 方法论

未来每次使用 AI，都要沉淀：

| 类型 | 沉淀物 |
|---|---|
| 问题分析 | 讨论记录 |
| 方案决策 | final.md |
| 执行过程 | implementation plan |
| 复盘经验 | growth journal |
| 可复用能力 | skill / agent profile |

长期看，这些会组成个人 AI 操作系统。

---

## 七、30 天提升计划

## 第 1 周：固定伙伴圆桌 MVP

目标：

- 输入主题
- 5 个固定 Agent 轮流真实发言
- 每条消息间隔 5-10 秒
- 用户可插话
- 输出 final.md

验收：

- 能跑完一次完整讨论
- 每条消息都有真实来源标记
- 网页能实时展示

---

## 第 2 周：状态和恢复

目标：

- session 可恢复
- 中断后可继续
- 用户插话可追踪
- 每轮有状态文件

验收：

- 关闭服务后重新打开还能看到历史
- 能继续未完成讨论

---

## 第 3 周：动态专家

目标：

- 主持人根据主题选择专家
- 支持临时 Agent profile
- 固定伙伴和动态专家可混合

验收：

- 不同主题生成不同专家阵容
- 专家输出进入统一日志

---

## 第 4 周：知识沉淀

目标：

- 每次讨论生成 final.md
- 重要结论自动归档
- 形成成长日志和方法论目录

验收：

- 每天有一条成长记录
- 每周能回看能力变化

---

## 九、给自己的建议

1. 少堆功能，多做闭环。
2. 少做“看起来像 Agent”的模拟，多追问真实执行链路。
3. 每个新想法都要落成：输入、过程、输出、复盘。
4. 保持角色和上下文解耦。
5. 优先做固定伙伴系统，再做动态专家。
6. 每天记录一次 AI 能力变化。
7. 把 AI 当作长期工作系统，而不是临时聊天工具。

---

## 十、结论

当前最重要的判断：

> 我已经从 AI 工具使用者，进入 AI 工作流设计者阶段。下一步的关键，不是学更多工具，而是把已有能力整合成一个可运行、可观察、可复盘的 Agent Runtime。

如果固定伙伴圆桌 MVP 跑通，就会形成一个新的基础能力：

```text
先讨论清楚 → 再写计划 → 再执行 → 再复盘沉淀
```

这会成为个人 AI 操作系统的核心雏形。
